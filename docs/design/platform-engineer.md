# 设计：平台工程师

状态：已实现
范围：`engineer.py`（新）、`self_repair.py`、`leading.py`、`supervisor.py`、`api.py`、`frontend/engineer.tsx`（新）

## 1. 为什么要加

修改 Super Partner 自身代码的能力原来只藏在任务的诊断里：某一步失败，诊断判断是平台的问题，
才会在隔离副本里改代码，检查通过后自动生效。这样有三个缺口：

1. 用户不能直接让它修一个缺陷或者加一个功能，只能先跑一个会失败的任务。
2. 负责人发现 Super Partner 缺少某种能力（一个工具、一个模型渠道、一种步骤），只能把那一步判为无法完成。
3. 平台改了什么只记在发起修复的那个任务里，看不到全部历史；生效后也不会提交到 git。

## 2. 角色

**平台工程师**专门修改 Super Partner 自身，和负责人并列，但不属于任何一个任务。

| | 负责人 | 平台工程师 |
|---|---|---|
| 管什么 | 一个任务，从规划到结束 | Super Partner 本身 |
| 改哪里 | 任务的项目目录 | Super Partner 源码的隔离副本 |
| 同一时间 | 每个任务一个 | 一次只做一件，其余排队（任务里的修复不排队，见第 4 节） |

## 3. 工单（`EngineerJob`）

每件工作是一张工单，存在 `engineer_jobs` 表里。

- 类型 `kind`：`repair`（修复缺陷）或 `component`（添加组件：模型或渠道、工具和技能、界面功能、调度和流程）。
- 来源 `origin`：`user`（用户在平台工程师页面提出）、`lead`（负责人在任务中请求）、`diagnosis`（任务的诊断判断是平台问题）。

状态：

```
组件：  queued → planning → plan_ready ──批准──→ queued → editing → validating → ready ──应用──→ applying → applied
                              │ 回复修改 → planning              │ 回复修改 → editing
修复：  queued → editing → validating → applying → applied                (检查通过就自动生效)
任一阶段：needs_input（工程师提问，回复后继续）、failed、rejected（用户放弃）、cancelled
```

- **planning**：工程师读代码，写方案（目标、改哪些文件、怎么测、需要用户决定的事），不改任何文件。
- **editing / validating**：沿用 `platform_repair.py`：在隔离副本里改，必须带测试，独立的沙箱检查
  （语法、数据库兼容、后端测试、前端测试、构建），不通过就把失败输出交回给工程师再改，最多
  `platform_repair_attempts` 次。
- **ready**：组件已通过检查，等用户看过改动后点"应用"。修复跳过这一步。
- **applying**：和原来的平台修复一样，等在途的模型调用结束，重启服务，健康检查不过就回滚。
- 应用时如果源码已经被别的改动更新过，工单回到 editing，用新的副本按已批准的方案重做。

## 4. 三个入口

1. **用户**：平台工程师页面上提出修复或组件需求。花费记在工单自己的预算上（默认
   `engineer_budget_usd`），默认用会员 CLI，不额外花钱。
2. **负责人请求组件**：新的决定 `request_component`。任务暂停（`ExecutionRun.engineer_job_id`），
   工程师先写方案，用户在平台工程师页面或任务的负责人面板里批准。工单结束（应用、失败或被放弃）
   后结果交回负责人，由它决定那一步怎么办。
3. **任务里的平台修复**：负责人决定 `repair_platform`，或者诊断判断 `STATUS: PLATFORM_REPAIR`。
   流程不变（`_fix_platform`，在任务的诊断里进行，花费记在任务上，不排队，因为任务在等它），
   只是同时记一张 `repair` 工单，在平台工程师页面上可见。生效或失败后：负责人请求的修复交回负责人
   决定（和环境修复一样），其余按原来的方式继续任务。

## 5. 生效后提交到 git

工单应用成功后（新进程启动后，`_finish_platform`），由程序在当前分支上提交这次改动的文件
（`git commit -- <files>`，不带上用户已暂存的其他改动），提交信息写明工单标题和"平台工程师"。
不推送。没有 git 仓库、或提交失败时，只在工单里记一条说明，不影响生效。

## 6. 护栏

- 模型只改隔离副本，从不碰在用的源码、任务数据、凭据、git 历史和服务。
- 同一时间只有一个改动等待生效（`platform_pending`）。
- 改动必须带测试，不能删除原有测试；检查由程序独立运行。
- 组件生效前必须经用户确认；负责人请求的组件，方案也要用户批准。
