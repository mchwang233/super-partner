# 项目员工与委派

目标：负责人先决定员工数量、职责、能力、模型及 Skill，再规划工作包并分配员工；员工可将新发现的子任务交给其他员工。项目增加“员工”页展示分工和委派关系。

实现范围：models/config 保存兼容的员工配置；team 负责组队、分配、共享上下文和委派校验；planner/outline/refining/replan 延续员工分工；executor 保存委派、释放执行名额、等待验收后继续；quality/skills/preflight 提供对应知识；frontend 展示分工、模型、Skill、任务状态和父子任务。

验证：组队先于划分；不同员工模型保持；共享需求和既有交付可见；委派、幂等、失败、取消、重启及累计预算；无循环依赖或越界文件；旧记录兼容；员工页实际 DOM 交互；全量后端和前端测试及构建。

风险控制：员工不会获得额外权限；子任务属于同一项目并继承权限及预算约束；父任务等待期间释放名额；限制委派深度、总量；验收通过后才能继续父任务。旧任务不自动重写，新项目通过 employee_teams 设置启用。


## 已实现的流程

`employee_teams` 默认为 false。启用后，新任务负责人先发起独立的 TEAM_SETUP 决策，确定 1 至 team_max_employees 名员工（默认最多 8 名），然后在同一负责人会话中规划任务。模型及 Skill 必须来自可用目录，职责和能力名称不改变底层模型评分。未知的工具知识交给原有预检、Skill 复用及发现流程。团队决策失败不会悄悄回退成另一种任务流程。

启用 `direct_task_planning` 时，负责人直接给出任务事项、员工、依赖、交付和验收条件，随后按依赖执行，不再细化。未启用时保留下面的大项兼容流程。直接计划不会把整个任务强制切成每文件、每命令的小步骤；执行中必要的员工委派继续适用。后续规划失败换负责人时，复用已经完成并校验的组队结果。

每个大项有默认员工，细化后的任务可显式指定其他员工，未指定时继承所属模块员工。调度保留负责人指定的模型，并核验能力、工具通道及上下文；恢复流程的显式模型切换记录在任务上。每名员工同时执行一个任务，同一提供商的执行任务数量遵守配置的并发容量。预算、文件互斥、独立验收等原有检查继续生效。

员工上下文包含完整用户需求、项目规划上下文、共享协作约定、全项目模块接口和验收标准、人员分工以及各任务状态与已接受交付摘要。原始工具会话仍按任务隔离；员工跨任务复用的是已记录的交付与参考文件。每次启动或续做都读取最新共享信息。指定 Skill 的指令保存到员工记录，预检后补充工具所需的 Skill。

共享对齐资料保存在计划中的 team_brief、parts 的 provides/acceptance、员工和任务记录中，并在员工页展示；这些字段是当前唯一数据源，不额外生成可能与计划不一致的工作目录副本。

## 委派协议

API 和 CLI 执行者均可用同一协议交出当前执行权：最终回复第一行为 `DELEGATE_TASKS`，后接一个 JSON 对象，包含稳定 request_id、reason、tasks。每项子任务使用现有工作包字段，并可指定 employee_id；缺省时从其他符合能力和可用性条件的员工中，按负载和预计费用分配。一次最多 3 个子任务，每任务默认最多 6 次委派，嵌套深度默认最多 3 层，同时受既有项目任务总量约束。

子任务依赖仅可引用已经通过的项目节点或本批更早的子任务；原任务增加对子任务的依赖并转为待执行，保存一个 delegated 尝试（不算失败）。发布前在计划副本上校验职责、模型、相对文件路径、依赖环及产物契约，全部通过才一次性保存。重复 request_id 不创建重复任务，改变内容必须使用新的 request_id。取消或旧 generation 的迟到请求不能发布子任务。

原员工等待期间释放执行名额，子任务通过原有平台验收后原任务才继续。API 原任务保留原生会话，并接收子任务结果和最新项目上下文；重启后也能继续。子任务失败或阻塞不会被当作原任务完成。子任务及其复核调用费用计入项目预算，也计入所有带产物契约的委派祖先；工具轮次同样累计，重启不重置。不能可靠计数轮次的通道不能执行这种受限子任务。

## 页面

项目内的“员工”页展示员工职责、配置模型、能力、Skill、未细化的大项、具体任务及状态；任务行显示实际执行模型，保留恢复切换的可见性。委派任务显示发起员工和原任务，原任务显示等待的子任务。可搜索任务、打开执行详情和返回原任务，也可查看项目协作约定和模块接口。旧项目保持原计划，在页面中显示未分配员工的任务。
