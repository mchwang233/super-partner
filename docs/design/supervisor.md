# 设计：任务负责人（Supervisor）

状态：已实现（4 个阶段均已完成）
范围：调度层（`executor.py`、`diagnosing.py`、`recovery.py`、`review.py`、`planner.py`）

## 1. 为什么要改

现在的调度层是一个写死规则的状态机，中间穿插许多次性的模型调用，彼此不共享记忆：

| 判断者 | 何时出现 | 记忆 |
|---|---|---|
| 规划模型 | 任务开始时一次 | 规划完就结束 |
| 验收模型 | 每次尝试之后 | 无 |
| 验证步骤 | 计划里的步骤 | 无，结果直接触发返工 |
| 诊断 | 每次失败之后 | 无，每次靠历史摘要重新理解 |
| 进度检查 | 尝试跑满 10 分钟 | 无 |

由此产生的问题：

1. **标准不一致**：验收通过的工作被验证步骤打回，返工后又被验收打回（wordcount 任务实测）。
2. **同一情况结果不同**：`UNABLE`、`BLOCKED`、`NEEDS_INPUT` 加上执行模型自己的"无法完成"声明，谁先发现，就按谁的处理办法走。
3. **建议与规则冲突**：诊断建议换模型，但只有代码规则（连续失败两次）真正决定。
4. **计数器多且会被清零**：失败次数、连续失败、环境修复、返工轮数，被返工、手动诊断、重做等操作重置。
5. **返工无人把关**：验证不通过就机械地打回上游，只受"最多 2 轮"限制。
6. **计划不会调整**：拆得不合理的步骤只能反复重试。
7. **慢**：每次失败都启动一次新的诊断会话（1 到 15 分钟），每次都要重新理解任务。

## 2. 目标与非目标

目标：

- 规划任务的强模型成为这个任务的**负责人**，会话一直保留到任务结束。
- 失败怎么办、返工是否合理、要不要调整计划、是否算完成、何时问用户，都由负责人决定，并写明理由。
- 代码只做**护栏**（预算、权限、沙箱、卡死保护、防止无限循环），不再替负责人做判断。
- 判断集中到一处，第 1 节的问题 1、2、3、5、7 随之消失。

非目标：

- 不改执行层：执行模型仍是在沙箱里用工具干活的 Agent。
- 不改平台自我修复的验证与生效流程（`platform_repair.py`），只是改由负责人决定何时发起。
- 不追求负责人看到执行模型的全部对话，它看的是精简后的事件。

## 3. 角色

```
            用户
             │ 问题 / 回答
        ┌────┴─────┐
        │  负责人   │  规划 + 全程决策，会话保留到任务结束
        └────┬─────┘
   决策 ↓    │ ↑ 事件（精简）
 ┌───────────┼─────────────────────────┐
 │ 执行者（各步骤的 Agent）              │
 │ 验收者（每次尝试后给意见）             │  ← 提供意见和证据，不做最终决定
 │ 进度检查（运行过长时判断是否卡住）      │
 │ 环境修复（负责人决定修环境时才启动）    │
 └─────────────────────────────────────┘
 护栏（代码）：预算、沙箱与权限、联网开关、卡住即停、决策次数上限、额度识别
```

## 4. 负责人的会话

**选谁**：沿用规划模型的选择（`select_planner_model`，规划能力最高者）。优先会员 CLI，因为它不额外计费，自带上下文压缩，还能看工作目录里的文件。

**会话保持**：

| 类型 | 开始 | 继续 |
|---|---|---|
| Claude CLI | `claude -p --session-id <uuid> ...` | `claude -p --resume <uuid> ...` |
| Codex CLI | `codex exec ...`（去掉 `--ephemeral`，记录会话 ID） | `codex exec resume <id> ...` |
| API 模型 | 消息历史存入数据库 | 带完整历史继续请求，超过阈值时压缩旧事件 |

数据：`ExecutionRun.supervisor = {model_id, session_id, history（仅 API）, decisions: [...]}`。

**规划即上任**：规划在这个会话里完成，因此负责人从一开始就知道每一步为什么这样拆。

**恢复**：

- 服务重启：用保存的会话 ID 继续。
- 会话丢失（CLI 会话被清理、额度用完需换模型）：新开一个会话，用数据库里的计划、已完成步骤、决策记录生成一份"交接简报"，交给新负责人。
- 负责人暂时不可用：先按现有的保底规则（`recovery.py`）继续，可用后把这段时间发生的事件补发给它。

## 5. 事件与决策

**通知类事件**（不单独调用，攒到下一次需要决策时一起发）：步骤通过、进度检查判定"仍在推进"、换模型（额度用完）。

**需要决策的事件**（立即调用负责人）：

| 事件 | 附带的证据 |
|---|---|
| 尝试失败（被验收打回 / 报错 / 进度检查判定卡住） | 验收意见、错误、工具调用摘要、改动的文件 |
| 执行者声称"无法完成" | 它给的理由 |
| 验证步骤不通过 | 验证的结论、被验证步骤的验收意见 |
| 用户回答了负责人的问题 | 回答内容 |
| 全部步骤完成 | 各步结果摘要（由负责人确认整体是否达成目标） |

**决策**：负责人用 JSON 回答，代码校验后执行；格式不合法时让它重答一次，仍不合法则走保底规则。

```json
{"action": "retry | switch_model | rework | accept | unable | ask_user | repair_environment | repair_platform | replan",
 "node_id": "...", "model_id": "可选，switch_model 时", "targets": ["rework 时要重做的步骤"],
 "instructions": "交给执行者的具体要求", "question": "ask_user 时", "options": ["..."],
 "plan_changes": "replan 时：新增 / 删除 / 修改的步骤", "reason": "中文理由，展示给用户"}
```

- `retry`：同一模型带着指示再试。
- `switch_model`：换模型；可选模型列表由代码提供，负责人只能从中选。
- `rework`：返工指定步骤。负责人可以判定"验证提的是新标准或验证有误"，从而拒绝返工，改为 `accept`。
- `accept`：接受当前结果（包括验收没过、但负责人判断已达成目标的情况）。
- `unable`：判定这一步在当前环境中做不到，写明原因和需要用户做什么；其余步骤继续。
- `ask_user`：暂停并提问（取代 `BLOCKED` 和 `NEEDS_INPUT`）。
- `repair_environment`：启动环境修复（沿用现有的修复会话），修好后再试。
- `repair_platform`：Super Partner 自身有缺陷，走平台修复流程。
- `replan`：调整计划，比如拆分、合并、增删步骤；已完成的步骤保留。

所有决策写成 `run.decision` 事件，显示在任务时间线上，附带理由。

## 6. 护栏（代码保留）

- 预算、沙箱、权限、联网开关：不变。
- 进度检查判定卡住就停：不变（这是执行层的卡死保护）；停下之后由负责人决定怎么办。
- 额度用完、服务不可用：仍由代码识别并立即换模型，只通知负责人（快，不值得一次决策）。
- **决策次数上限**：每个步骤最多 5 次决策，整个任务最多 25 次；超过后暂停并问用户。这取代现在的失败次数、返工轮数等各种计数器。
- 负责人不可用时的保底：现有的 `recovery.py` 规则。

## 7. 现有机制的去留

| 现有机制 | 处理 |
|---|---|
| 每次失败自动诊断（`_repair` / `_repair_done`） | **删除**，由负责人决策；需要修环境时它发出 `repair_environment` |
| `recovery.after_diagnosis` | 改为执行负责人的决策（`apply_decision`） |
| 连续失败两次换模型 | 变成给负责人的默认建议，同时作为保底规则 |
| 验证不通过自动返工（`_send_back`） | 改为生成"验证不通过"事件，由负责人决定是否返工 |
| 验收模型 | **保留**：通过就直接接受；不通过时，验收意见作为证据交给负责人 |
| 诊断结论 `BLOCKED` / `UNABLE` / `NEEDS_INPUT` | 统一成负责人的 `unable` 和 `ask_user` |
| 失败次数、返工轮数、环境修复次数 | 由决策次数上限取代 |
| 手动"诊断"按钮 | 改为"问负责人"：把用户的问题发进同一个会话 |
| 进度检查、额度识别、平台修复流程 | 保留 |

## 8. 速度与成本

- 一次决策是在已有会话里追加一段消息，比新开诊断会话快得多：不用重新理解任务，也不用从头读代码。预计每次 20 到 60 秒；现在一次诊断要 1 到 15 分钟。
- 步骤通过不调用负责人，只在需要决策时调用。
- 发给负责人的都是精简事件（每个几百字），不发执行者的全部对话。CLI 会自动压缩上下文；API 负责人的历史超过阈值时，把旧事件压缩成摘要。

## 9. 分阶段实现

每个阶段都要求：全部测试通过、补上回归测试，并用一个真实任务验证。

1. **会话基础**：CLI 会话的开始与继续（Claude、Codex）、API 历史的保存、会话 ID 入库、重启后恢复、会话丢失后用交接简报重建。规划在负责人会话里完成。
2. **失败决策**：尝试失败时调用负责人，取代自动诊断；实现 `retry`、`switch_model`、`unable`、`ask_user`、`repair_environment`、`repair_platform`；决策显示在时间线上。
3. **返工把关**：验证不通过时交给负责人，实现 `rework` / `accept`。
4. **计划调整与收尾**：实现 `replan`；全部完成时由负责人确认整体目标；删除被取代的旧规则和计数器，更新 `docs/ARCHITECTURE.md` 和修复 skill。

## 10. 已确认

1. 负责人优先用会员 CLI；都不可用时用 API 模型（按 token 计费）。
2. 步骤验收通过就接受，不需要负责人确认。
3. 决策次数上限：每个步骤 5 次，整个任务 25 次。
4. 负责人调整计划时直接执行，在时间线上写明理由。

## 11. 实现情况

- 第 1 阶段：`supervisor.py`（会话、交接、裁剪），`ProviderRegistry.converse`、`CliChannelRegistry.converse`，规划在负责人会话里完成（`planner._plan_as_lead`）。
- 第 2 阶段：`leading.py` 的 `_decide` / `_apply_decision`，负责人提问复用诊断的问答界面，回答交回负责人。
- 第 3 阶段：验证不通过交给负责人，`rework` 可以只打回部分步骤并附上要求。
- 第 4 阶段：`replan.py`（增删改步骤，校验依赖不成环、已完成和正在运行的步骤不动），全部步骤完成后的 `_final_review`（`done` / `rework` / `replan`），界面上的"负责人"面板。

与第 7 节的差异：旧规则没有删除，而是保留为**兜底**。负责人不可用、连续两次回答格式不对，或者关闭了 `lead_decisions` 时，仍按原来的诊断、`recovery.py`、失败次数和返工轮数运行，任务不会因为负责人出问题而卡住。代码和配置注释里都标明了这一点。
