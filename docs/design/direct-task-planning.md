# 直接任务计划

目标：负责人先组队，再一次列出任务事项、员工、真实依赖、交付接口和验收条件。任务按依赖执行，不再生成等待细化的大项。员工因实际执行发现必要子任务时，保留现有委派机制。

改动：`task_planning.py` 复用任务解析、产物契约校验和一次纠错，生成可执行节点；`planner.py` 选择直接计划并保留已完成组队结果；`api.py` 保留员工指定的模型；`config.py` 提供默认关闭的直接计划设置和独立规划推理档、调用时限。现有进度图和员工页直接显示任务，无需新的展示层。

测试：组队先于任务；一个任务也可执行；依赖、验收与员工校验；产物输入输出和执行限额保留；执行调度不调用细化模型；创建和确认不改变员工模型；慢调用取消后才切换负责人。

风险：任务的实际执行可能比小步骤更长，仍受原有预算、验收、进度检查和产物限额约束。设置只作用于新计划，旧项目记录和旧细化流程继续兼容；已取消的项目不会自动恢复。尚未用真实模型做同请求速度对照。

## 并行（2026-10-26）

问题：mesh 项目的直接计划是 3 个 hard 任务排成一条线，两名员工轮流空等，覆盖率闭合一个任务失败 5 次、每次整体重来。

改动：提示词加入 `PARALLEL_RULE`（验证环境按接口契约与实现同时搭建；超过约 1 小时的 hard 任务按模块、配置、指标或目标族拆开，由汇总任务合并）。3 个以上任务、含 hard、完全串行且无 `serial_reason` 的计划在原有纠错轮退回一次，第二次回答直接采用，不会因此规划失败。规划说明写明最多几个任务可同时进行或串行原因。

风险：规则是对负责人的要求，拆分质量仍取决于负责人；只作用于新计划。
