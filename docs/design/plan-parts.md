# 设计：逐级拆分的计划

状态：已实现
范围：`outline.py`（新）、`planner.py`、`models.py`、`supervisor.py`、`replan.py`、`quality.py`、`frontend/plan-parts.tsx`（新）、`frontend/plan-graph.tsx`

## 1. 为什么要改

原来负责人一次给出一张平铺的计划，最多 30 个步骤。项目一大，问题就出来了：

1. 一次想清楚几十个步骤很难，步骤常常太大、太模糊，执行的模型只好去翻大量代码。
2. 进度页把所有步骤摊在一张图上，看不出整体做到了哪里。

## 2. 怎么拆

负责人在自己的那段对话里自上而下地拆分（`outline.plan_in_parts`）：

1. 先把整个需求拆成 1–8 个**大项**，例如数据层、接口、页面、测试。每个大项写明目标、完成标准，以及要等哪些更早的大项。
2. 然后逐个细化每一项（深度优先）。每个子项要么是**更小的项**，下一轮接着拆，要么是**任务**。
3. 最多拆 3 层（`MAX_DEPTH`），最深一层的子项必须都是任务。整个计划最多 60 个任务（`MAX_TASKS`）。

任务就是原来的步骤（`TaskNode`），必须满足：

- **独立**：执行的模型只看到任务说明、它点名的文件，以及前置任务的交付，看不到整个计划和项目，所以说明本身要完整。
- **明确**：只有一个具体结果，写清楚，不留猜测。
- **小**：有能力的模型大约 10–15 轮工具调用能做完；最多改 5 个文件、参考 8 个文件（`scope_problems`）。
- **能单独审核**：有验收标准，审核模型只看这个任务的结果和文件就能判断。

不满足的任务会退回给负责人重拆，最多两轮（`task_problems`）。格式不对的回复会让它在同一段对话里重答一次；还不行，就换下一个负责人，再不行就退回到原来一次出平铺计划的方式。

## 3. 怎么执行

只有任务会执行，调度方式不变。项只用来分组：

- 依赖只写在同一层的兄弟之间。等一个项，就是等它的"最后一批任务"，也就是项里没有被其他任务等待的那些（`Tree.last`）。最终交给执行器的仍是一张普通的任务依赖图。
- 每个任务记着自己所属的项（`TaskNode.part_id`），项记在 `TaskPlan.parts` 里。
- 任务的提示词会多一行"Part of: 后端 › 存储 (goal: …)"，只说明它在哪，不替代任务说明。
- 负责人看到的步骤列表会标出每步所在的项。调整计划时新增的步骤可以用 `part` 指定所属的项；不指定，就归到正在决策的那一步所在的项。

没有负责人时，计划仍是平铺的，`parts` 为空，界面也和原来一样。

## 4. 进度页

`PlanView`：

- 大项卡片按依赖分成阶段，从左到右排列，卡片之间画依赖连线。卡片上有完成数/任务数、进度条、进行中的个数、子项个数和花费。
- 每个大项可以就地展开，按计划顺序显示它的子项（编号如 1.1，也能展开）和任务；点任务打开原来的详情抽屉。概览栏有“全部展开 / 全部关闭”开关。
- 任务编号和"等待 02"始终按整个计划算，所以在哪一层看都一致。
