# 设计：逐级拆分的计划

状态：已实现
范围：`outline.py`、`refining.py`（新）、`planner.py`、`models.py`、`executor.py`、`routing.py`、`api.py`、`supervisor.py`、`replan.py`、`quality.py`、`frontend/plan-parts.tsx`、`frontend/plan-graph.tsx`

## 1. 为什么要改

原来负责人一次给出一张平铺的计划，最多 30 个步骤。项目一大，问题就出来了：

1. 一次想清楚几十个步骤很难，步骤常常太大、太模糊，执行的模型只好去翻大量代码。
2. 进度页把所有步骤摊在一张图上，看不出整体做到了哪里。

第一版改成了规划时由负责人逐个细化每个大项。又带来两个问题：规划很慢（小任务约 2 分钟，大项目十几分钟）；负责人按阶段划分大项（设计 → 实现 → 测试 → 报告），大项之间排成一条链，几乎不能并行。

## 2. 规划时：只划分大项

负责人在自己的对话里只做一件事：把需求拆成 1–8 个**大项**（`outline.plan_outline`），几十秒就能完成。要求：

- **按功能划分，不按阶段划分**：每个大项是结果里的一个模块、功能或组件（存储模块、一个接口、一个页面、一章报告），自带测试和检查。不要划出"设计""实现""测试""文档"这类横跨全部内容的大项，只有"把各部分集成起来"和最终报告可以单独成项。
- **尽量能同时开始**：一个大项只等它确实需要的大项。
- **对外提供（`provides`）**：其他大项只能依据这份约定来对接，因为它们看不到本项的任务。内容包括本项拥有的文件，以及确切的名字、函数签名、接口和字段、数据和文件格式、命令。
- **规模（`size`）和主要能力（`capability`）**：预计有几个任务，用来在确认前估算费用（`routing.part_estimate`）。确认时的预算检查也会算上未细化的大项（`TaskPlan.unsplit_cost`）。

规划用的原始内容（需求、项目上下文、项目概况）存在 `TaskPlan.request` 里，执行时细化要用。

## 3. 执行时：所有大项同时细化

任务开始执行时，所有还没细化的大项一起开始细化（`refining.py`）。每个大项另开一段负责人对话，优先用这个任务自己的负责人模型：

1. 第一条消息是角色说明、任务规则、大纲（每个大项的目标和"对外提供"）、本项名称，以及需求和上下文，然后要求拆分本项（`outline.refine`）。
2. 每个子块要么是**更小的项**，下一轮接着拆（深度优先，在同一段对话里），要么是**任务**。最多 3 层（`MAX_DEPTH`），最深一层必须都是任务；整个计划最多 60 个任务（`MAX_TASKS`）。
3. 细化完，任务分配好模型就加进计划，按依赖开始执行。哪个大项先细化完，它的任务就先跑。
4. 细化失败（换了几个模型都不行，或者没有模型能做其中某个任务）时，任务暂停，并写明原因；继续执行会再试一次。

细化在执行器的主循环里跟步骤一起跑，暂停、取消、继续都沿用原来的处理方式；正在细化的大项不占步骤并发名额。

任务就是原来的步骤（`TaskNode`），必须满足：

- **独立**：执行的模型只看到任务说明、它点名的文件，以及前置任务的交付，看不到整个计划和项目，所以说明本身要完整。
- **明确**：只有一个具体结果，写清楚，不留猜测。
- **小**：有能力的模型大约 10–15 轮工具调用能做完；最多改 5 个文件、参考 8 个文件（`scope_problems`）。
- **能单独审核**：有验收标准，审核模型只看这个任务的结果和文件就能判断。

不满足的任务会退回重拆，最多两轮（`task_problems`）。格式不对的回复会在同一段对话里重答一次；还不行，就换下一个模型。划分大项时如果所有负责人都失败，就退回到原来一次出平铺计划的方式。

## 4. 怎么执行

只有任务会执行，调度方式不变。项只用来分组：

- 依赖只写在同一层的兄弟之间。等一个项，就是等它的"最后一批任务"，也就是项里没有被其他任务等待的那些（`Tree.last`、`outline.last_tasks`）。
- 大项之间的等待，要等两边都细化完才能连到具体任务上（`outline.link`，只增加依赖，不会删掉负责人自己加的）。在那之前，等待一个未细化大项的任务不会开始（`outline.waits_on_unsplit`）。最终交给执行器的仍是一张普通的任务依赖图。
- 每个任务记着自己所属的项（`TaskNode.part_id`），项记在 `TaskPlan.parts` 里。
- 任务的提示词会多一行"Part of: 后端 › 存储 (goal: …)"，只说明它在哪，不替代任务说明。
- 负责人看到的步骤列表会标出每步所在的项。调整计划时新增的步骤可以用 `part` 指定所属的项；不指定，就归到正在决策的那一步所在的项。

没有负责人时，计划仍是平铺的，`parts` 为空，界面也和原来一样。

## 5. 进度页

`PlanView`：

- 大项卡片按依赖分成阶段，从左到右排列，顶部对齐。卡片之间只画直接依赖（能经别的大项推出的依赖不画，以免连线穿过卡片背后），连线接在卡片标题处，展开时不动。卡片上有完成数/任务数、进度条、进行中的个数、子项个数和花费。
- 每个大项可以就地展开，按计划顺序显示它的子项（编号如 1.1，也能展开）和任务；点任务打开原来的详情抽屉。概览栏有“全部展开 / 全部关闭”开关。
- 还没细化的大项显示"待细化"（虚线边框）、"细化中…"或"细化失败"，以及预计任务数；展开后显示它对外提供什么，失败时显示原因。概览栏会写明还有几个大项待细化、预计多少任务。
- 任务编号和"等待 02"始终按整个计划算，所以在哪一层看都一致。
